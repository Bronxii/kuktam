## Acknowledgment audit — backend ownership preserved

Inspected installed 0.5.3 source, especially
`in_app_purchase_android_platform.dart`, `google_play_purchase_details.dart`,
`billing_client_wrapper.dart`, and native Gradle configuration.

1. Generic Android `completePurchase` is NOT mere local bookkeeping. Unless
   `billingClientPurchase.isAcknowledged` is already true, it calls
   `BillingClient.acknowledgePurchase(serverVerificationData)`.
2. Non-consumable launch does not acknowledge or consume. Consumable auto-consume
   is a separate generic-plugin path, which is not instantiated/used here.
3. Android event delivery has no local unfinished StoreKit-style queue that
   requires completePurchase. Completion is not required to release the stream.
4. Backend acknowledgment satisfies Play's requirement. An already received DTO
   may still contain the old acknowledgement flag; it is not authoritative and
   is not used for entitlement or client completion decisions.
5. A new owned query can report backend-acknowledged ownership. It still goes
   through backend verification and trusted entitlement refresh, not direct Pro.
6. This adapter uses public Android wrappers without invoking completePurchase,
   acknowledgePurchase, consumeAsync or buyConsumable. Tests spy on native
   acknowledgment and consume and require zero calls for purchase and restore,
   for both acknowledged and unacknowledged evidence.

No ACK contract conflict was found. Backend timely ACK and actual Play behavior
still require later licensed-device validation; local tests do not replace that.

## Data and flow contracts

- Central product: `kuktam_pro_lifetime`, package `com.bronxii.kuktam`.
- ProductOffer carries Play localized display price, currency and title. No price
  constant. Missing product is distinct from unavailable store/query failure.
- Evidence is minimal Android product/package/token/opaque binding. No full
  purchase DTO, order history, signature or client purchase timestamp retained.
- PENDING never verifies/grants. PURCHASED and RESTORED verify, then refresh
  N5.1. Even backend `verified` cannot directly set Pro; a refreshed Free result
  is valid. Flow `completed` is not an entitlement assertion.
- Gateway outcomes include pending, rejection, deletion, binding conflict,
  support, temporary/config failure and malformed response. Unknown exceptions
  are sanitized. Gateway has no UID request argument.
- Billing failure mapping uses typed BillingResponse values, including canceled,
  already-owned, disconnected/timeout/service, network, unavailable product/store,
  configuration and unknown. Raw error/debug messages never enter flow state.
- Already-owned invokes owned recovery. Explicit restore is also explicit retry:
  it reacquires evidence rather than persisting a purchase token history.
- Purchase/backend errors never reset an existing N5.1 Pro/grace entitlement.
  Account deletion outcomes block further billing operations; auth/entitlement
  lifecycle cleanup remains with the existing host/N5.1 policy, not this service.

## Auth/session integration contract for N5.3

The future host must own exactly one orchestrator/Android adapter. Never create
one per screen. There is one stream subscription and one lazy native connection.

1. Invalidate current authenticated transport credentials/session and call
   `bindSession(null)` synchronously before logout/account switch.
2. Clear/initialize N5.1 repository for the new UID.
3. Obtain the opaque `v1_...` account binding from an authenticated backend
   operation. Do not compute HMAC in Flutter or pass raw UID to Play.
4. Supply a PurchaseSession whose `isCurrent` checks the exact auth session,
   not just equality of UID, and whose gateway captures that session's auth
   credentials. The backend must derive UID from verified auth, not request JSON.
5. Bind it, then load offer/query owned purchases as appropriate at startup/resume.

Every asynchronous result checks generation, current auth predicate, repository
UID and deletion state. The native launch checks session again after connecting.
N5.1 separately fences a trusted refresh that overlaps a user change.

Global Play callbacks have no Firebase session identifier: evidence must match
the current opaque account binding before automatic verification. Unbound or
other-account unsolicited evidence is ignored. Explicit session-bound restore
may send old-account ownership to the backend to return conflict/support;
it never transfers ownership. Unbound cancellation/error callbacks only update
an awaiting purchase flow and cannot affect entitlement.

## Concurrency, recovery and privacy

- One in-flight verification per token. Different evidence is serialized, with
  a maximum backlog of four; excess callbacks require explicit owned recovery.
  This prevents reordered verification results and unbounded verification storms.
- Dedupe is in-flight only, not a permanent local ledger. Later replay may be
  reverified; backend idempotency is the final durable guard.
- On UID switch, old results are discarded and old queued work cannot dispatch.
  A new session can progress without waiting for an old network call.
- Configurable 30-second gateway timeout; no automatic verification retry loop.
  Native operations have a configurable 20-second timeout. A timed-out request
  may still finish externally; its result does not grant entitlement locally.
- Pending operations recover through owned query after restart. There is no
  persisted pending purchase queue and no dependency on an old callback.
- Token-bearing evidence/keys exist only during queued/in-flight verification or
  an owned query. No token cache/history/logging/analytics. Strings cannot be
  securely zeroed in Dart; external plugin/future memory lasts until released/GC.
- Gateway/network implementations must not log requests or raw exceptions and
  must discard credentials/evidence on session invalidation. N5.2 has fake gateway
  only; it does not claim to authenticate client-supplied session objects.
- Dispose fences old callbacks, cancels stream and closes native connection;
  a late connection setup after dispose is closed again.
